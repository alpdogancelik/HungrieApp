## Result

The Customer app now uses Firebase only for authentication and Supabase for catalog, profile, addresses, favorites, orders, reviews, and Customer notification registration. Repository selection always chooses Supabase for application data, including missing or disabled configuration, so startup fails closed rather than selecting Firestore. Normal Customer screens contain no Firebase application-data imports.

After Firebase authentication, the root gate resolves `get_my_access_context_v1()`. An unmapped identity reuses a locally persisted UUID while calling `bootstrap_my_customer_account_v1()`. Only an active Customer mounts private navigation. Restaurant/Admin and revoked identities are signed out; suspended, configuration-error, and retryable availability states have dedicated bilingual gates. `/admin`, `/restaurantpanel`, and `/courier` routes remain in the source for Phase 12 compatibility but cannot mount from the Customer root. Restaurant notification payloads and preferences are ignored.

The public catalog v2 projection exposes active ingredients, removable flags, option groups, selection limits, values, price deltas, and menu-definition revision. The menu UI enforces required and maximum selections, single/multiple choice, and removable ingredients before adding a line. Cart identity canonically sorts option and removed-ingredient choices. Checkout cannot proceed without `quote_order_v2()` and submits only IDs, quantities, address, payment, notes, and a stable operation UUID to `create_order_v2()`. The same request reuses the UUID after an uncertain response; changed cart or checkout input receives a new UUID.

Native startup calls `get_client_release_policy_v1("customer", platform, buildNumber, 2)` before mounting navigation. Failed policy/configuration checks block with retry. A required update blocks with the iOS App Store ID `6759683384` or Android package `com.hungrie.app`. Web skips the native build policy while retaining fail-closed configuration validation.

## Rollback

If the additive migration fails, stop before client builds and forward-fix migration history; use the restricted backup only if a forward fix cannot safely recover. If a preview build fails qualification, keep it internal and leave the currently supported Customer configuration unchanged. Restore every temporary minimum-build or maintenance-policy change immediately after its test. Legacy contracts remain live until later enforcement/removal phases, so rollback must never weaken canonical authorization.
